제시해주신 의문점들은 시스템 아키텍처와 메모리 계층 구조의 본질을 꿰뚫는 매우 날카로운 질문들입니다. OS 및 시스템 최적화 관점에서 하드웨어의 동작 원리와 정확히 맞닿아 있습니다.

질문하신 순서대로 하나씩 명확하게 해답을 드리겠습니다.

### 1. Interleaved Layout의 NoC 병목 및 성능 저하 원인

**Q: 요청이 분산되더라도 특정 타일 보유 코어에 동시 요청이 몰리는 것은 똑같지 않은가? 총 요청 수는 같은데 왜 병목이 줄어드는가? 그럼에도 DRAM보다 느린 이유는?**

* **시간적 부하 분산 (Staggering Effect):** 64개의 워커 코어가 16개 타일로 구성된 '하나의 청크'를 순차적으로 읽는다고 가정해 보겠습니다.
* **Sharded:** 16개 타일이 모두 '코어 A'에 있습니다. 코어 A의 NoC 포트는 16번의 스텝 내내 64개의 요청을 연속으로 두들겨 맞으며 대기열(Queue)이 터져버립니다.
* **Interleaved:** 타일 0은 코어 0, 타일 1은 코어 1에 흩어져 있습니다. 스텝 0에서는 코어 0에 64개의 요청이 몰리지만, 스텝 1에서는 코어 1로 병목이 이동(Migration)합니다. 코어 0은 그사이 숨을 돌리고 큐를 비웁니다. 즉, 순간적인 동시 접근(64개)은 같아도 **지속적인 포트 점유 시간이 짧아져 전체적인 파이프라인 정체가 완화**되는 것입니다.


* **그럼에도 Baseline(DRAM)보다 느린 이유:** 앞서 분석했듯, 핫스팟이 이동하더라도 "특정 찰나의 순간에 단 하나의 NoC 포트가 64개의 요청을 직렬(Serial)로 처리해야 한다"는 하드웨어적 한계 자체는 변하지 않기 때문입니다. DRAM 하드웨어 컨트롤러는 이 64개의 동일 주소 브로드캐스트 읽기 요청을 하드웨어 단에서 병렬로 뿌려줄 수 있는 인프라를 갖추고 있습니다.

### 2. Sharded Layout의 토큰 범위 담당

**Q: 각 티어(Tier)는 서로 Disjoint한 토큰 범위를 담당하는가?**

* **네, 정확합니다.** 시퀀스(Sequence) 길이를 기준으로 공간을 분할합니다.
* 예를 들어 Tier 0(Sink)은 0~31번 토큰, Tier 1은 32~63번 토큰, Tier 2는 64~127번 토큰을 담당하는 식입니다. 워커 코어는 현재 읽어야 할 토큰의 인덱스(Global Sequence Tile)가 어느 범위에 속하는지 계산하여 해당 티어가 위치한 코어로 NoC 요청을 보냅니다.



### 3. `paged_update_cache` 함수의 정체

**Q: 우리는 Paged Attention을 안 쓰는데 이 함수의 기능은 무엇인가? DRAM Baseline에서도 쓰이는가?**

* **명칭의 오해:** 여기서 'Paged'는 vLLM의 동적 메모리 할당(Paged Attention)을 의미하는 것이 아닙니다. 텐스토렌트 커널 명명 규칙상 "거대한 Ring Buffer 텐서의 특정 인덱스(페이지/슬롯)에 새로 생성된 1개의 토큰 K/V 값을 업데이트해 넣는 동작"을 의미합니다.
* **사용처:** **DRAM Baseline에서도 똑같이 사용됩니다.** 디코드 스텝에서 토큰 1개가 생성될 때마다, 그 토큰의 K/V 값을 DRAM에 있는 거대한 KV 캐시 텐서의 `cur_pos` 인덱스에 써넣어야 하기 때문입니다. 과거에는 이 함수를 호출할 때 Python 단에서 Host Sync가 발생해 병목이었으나, 현재는 Device-side로 최적화되어 오버헤드가 사라졌습니다.

### 4. `l1_only_mode`와 Circular Buffer 할당 스킵

**Q: L1-to-L1 복사가 일어나는데 어떻게 CB 할당을 스킵한다는 것인가?**

* **불필요한 DRAM 전용 CB 제거:** SDPA 커널이 하이브리드(DRAM + L1)로 동작할 때는, L1에서 데이터를 받아올 CB(`cb_k_in_l1`)뿐만 아니라, DRAM에서 데이터를 끌어와 임시로 담아둘 **DRAM 전용 CB(`cb_k_in_dram`)와 페이지 추적용 메타데이터 버퍼**를 L1의 정적 공간에 무조건 함께 할당해 두어야 합니다.
* **Footprint 축소:** `l1_only_mode` 플래그를 켜고 커널을 컴파일하면, C++ 커널 단에서 이 DRAM 전용 CB들과 관련 스테이징 버퍼들을 아예 생성하지 않습니다. 연산기(Math Engine)로 들어가는 최종 CB(`cb_k_in`)로 L1 데이터만 바로 복사되도록 파이프라인이 단순화되므로, 커널이 차지하는 고정 L1 면적(Footprint) 자체가 수십~수백 KB 줄어들어 그만큼 KV 캐시를 위한 가용 공간이 늘어납니다.

### 5. 할당 가능한 최소 크기 (Sharded vs Interleaved)

**Q: 왜 Sharded는 최소 크기가 Interleaved보다 큰가? 더 작게 설정할 수는 없나?**

* **배치 그레뉴얼리티(Granularity)의 차이:** Interleaved는 데이터를 물리적인 **1개 타일(Tile, 예: 2KB) 단위**로 칩 전체 뱅크에 라운드 로빈으로 흩뿌립니다. 따라서 아주 작은 용량도 할당 가능합니다.
* **Sharded의 제약:** Sharded 텐서는 텐스토렌트 구조상 2D 그리드에 매핑되어야 하며, 각 코어당 최소 **1개의 '타일 로우(Tile-row)' 단위**를 가져야 합니다. 여러 개의 KV 헤드(Head)와 타일 구조를 고려할 때 이 최소 단위 자체가 수십 KB 수준으로 큽니다. 코어당 '반 개의 타일'을 할당하는 식의 텐서 매핑은 아키텍처 상 지원하지 않습니다.

### 6. Prefill vs Decode & Attention Sink 개념

**Q: Prefill은 User Input이고 Decode는 Output인가? Sink는 어떤 부분인가?**

* **Prefill vs Decode:** 정확합니다. Prefill은 사용자가 입력한 프롬프트(User Input) 전체를 한 번에 병렬 처리하여 초기 KV 캐시를 쌓는 과정입니다. Decode는 그 이후부터 모델이 1토큰씩 자가회귀적(Autoregressive)으로 Output을 생성하는 과정입니다.
* **Attention Sink:** User Input의 가장 첫 부분(보통 토큰 인덱스 0~31)을 의미합니다. LLM의 어텐션 메커니즘 특성상, 문장의 초기 토큰들이 전체 문맥의 구조를 잡아주는 닻(Anchor/Sink) 역할을 합니다. 링 버퍼 용량이 꽉 차서 중간 토큰들을 덮어쓰기(Evict) 하더라도, 이 첫 32개의 Sink 토큰만큼은 절대 지우지 않고 영구 보존해야 모델의 출력 품질이 무너지지 않습니다 (StreamingLLM 논문의 핵심).

### 7. Hybrid Approach (Interleaved + 남는 코어 Sharded) 타당성

**Q: Interleaved로 깔고, 여유 공간이 더 많은 코어에만 추가로 KV 캐시를 Shard 하는 방식은 합리적인가?**

* **OS/메모리 계층 관점의 평가:** NUMA 아키텍처나 Tiered Memory 시스템에서 매우 흔하게 쓰이는 훌륭한 시스템 소프트웨어적 발상입니다. 공간 낭비를 0%로 만들 수 있는 이론상 완벽한 배치입니다.
* **가속기 환경에서의 현실성 (합리성 부족):** 불행히도 현재의 결정론적 가속기(Deterministic Accelerator) 환경에서는 치명적인 성능 저하를 유발합니다.
* 이 구조를 구현하려면 SDPA 읽기 커널 내부 루프에 동적 분기문(Dynamic Branching)이 들어가야 합니다. *"지금 읽을 토큰 X가 전체 칩에 깔린 Interleaved 베이스 공간에 있나? 아니면 코어 Y에만 있는 Sharded 추가 공간에 있나?"*
* 연산기(RISC-V) 내부의 극도로 타이트한 이너 루프(Inner loop)에서 주소 매핑 규칙이 이원화되면, 명령어 분기 예측 실패와 클록 사이클 낭비가 극심해져 얻어낸 메모리 용량의 이점을 연산 지연(Latency)이 전부 갉아먹게 됩니다. 가속기에서는 "버려지는 메모리가 있더라도 메모리 접근 수학 공식(Address Math)을 무조건 단순하고 통일성 있게 유지하는 것"이 성능의 핵심입니다.
